# Easel for the web

The offline, installable web version of Easel: the Apple apps' own drawing engine, Paintbrush (`../Paintbrush`), compiled to WebAssembly, behind a web interface built on the Atelier design system in Easel's orange. No Node packages: the build is Swift and a shell script, and the page is plain HTML, CSS and JavaScript modules. It follows Tables', Libretto's and Dazzle's web apps file for file.

- [PLAN.md](PLAN.md): the porting plan and where it stands.
- [design/](design/): the design system. Rules are in `design/DESIGN.md`.

## Layout

| Folder | What's in it |
| --- | --- |
| `index.html`, `manifest.webmanifest`, `sw.js` | The page, the install manifest and the offline service worker |
| `app/` | The window: canvas, Layers inspector, files, strings |
| `engine/` | The engine's WebAssembly interface (Swift), its WASI host, text host, worker and loader (JavaScript), and smoke tests |
| `engine/swift/Sources/Portable/` | Stand-ins for the Apple frameworks Paintbrush imports (see below) |
| `strings/` | The web app's own string catalogue (`.xcstrings`, five languages); everything else comes from `Shared/Support/Localizable.xcstrings` |
| `design/` | Design tokens, components, menus, lint and specimen |
| `build/`, `dist/` | Generated by `build.sh`, not checked in: the build, and the site to publish |
| `deploy/`, `wrangler.jsonc` | Publishing to Cloudflare: headers, `robots.txt`, sitemap, the CI build |

## Setting up

The engine builds with the open-source Swift toolchain and its Swift SDK for WebAssembly, of exactly the same version. Xcode's own toolchain can't use the SDK.

1. Install the swift.org toolchain, for example Swift 6.4.2 from [swift.org/install](https://www.swift.org/install/). On a Mac it installs to `~/Library/Developer/Toolchains`.
2. Install the matching Swift SDK for WebAssembly:

   ```sh
   swift sdk install https://download.swift.org/swift-6.4.2-release/wasm-sdk/swift-6.4.2-RELEASE/swift-6.4.2-RELEASE_wasm.artifactbundle.tar.gz \
       --checksum 83baca83553f8c443cda7b84800912e6e709c3acd2e7ebf277794ca5836c0da5
   ```

`build.sh` looks for these at their default locations; set `SWIFT_TOOLCHAIN` and `SWIFT_SDK` to use others. It also fetches zlib and SQLite (`engine/vendor.sh`, checksummed) the first time.

## Building and running

```sh
./build.sh                # engine, strings and offline file list, into build/
./build.sh --skip-engine  # after changing only the page's own files
npm run serve             # http://localhost:8000 (the specimen is at /design/)
npm test                  # engine smoke tests; pass .psd/.pxd/.png/.jpg paths to open them too
npm run lint:design       # design rules
```

On `localhost` the offline service worker only installs when the address has `?offline`, so that edits show up without a rebuild. Anywhere else it always installs. On `localhost` the window is also `window.easel` in the console.

## Deploying

The app is published at [easel.atelier.ktgk.app](https://easel.atelier.ktgk.app) as a Cloudflare Worker that serves only static files (`wrangler.jsonc`). The custom domain is created by the first deploy.

- `build.sh` assembles the site into `dist/`. The engine goes up gzipped (`build/easel-engine.bin`, about 20 MB; not named `.gz`, which Cloudflare answers with a bot challenge) because Cloudflare serves files of at most 25 MiB; the worker decompresses it. `build.sh` stops if any file is too large.
- Every push to `main` that touches `Web/` or `Paintbrush/` builds, tests and deploys through `.github/workflows/web.yml`. Pull requests are built and tested only. The workflow needs the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
- To deploy by hand from a Mac: `./build.sh && npx wrangler deploy`.

## How it fits together

- **Engine.** `engine/swift/Sources/EaselWasm` links Paintbrush into a WebAssembly reactor that exports a few C functions. Requests and responses are JSON, with file contents and pixels passed as raw bytes alongside.
- **Paintbrush, unchanged.** `Sources/Paintbrush` is a link to `../Paintbrush`, compiled exactly as the Apple apps compile it. What it imports from Apple's SDK is supplied by modules of the same names in `Sources/Portable`, which implement only what Paintbrush uses:
  - `CoreGraphics`: bitmap contexts drawn in software (scanline polygons with 16 sample rows a pixel, every blend mode, clipping masks, transparency layers, shadows, gradients, mipmapped image drawing), paths with stroking and dashing, images, colours, `String(localized:)` over the page's string tables, and Foundation pieces WebAssembly lacks (`FileWrapper`).
  - `CoreImage`: an image is a recipe asked for regions, as in Core Image; contexts draw a tile at a time, in linear light. Every filter Paintbrush names is implemented.
  - `ImageIO`: PNG, JPEG and GIF in Swift. Other pictures (HEIC, WebP, TIFF, AVIF) are decoded by the browser and handed over as pixels.
  - `AppKit` and `CoreText`: the text system, which asks the page to measure and draw type (`engine/text.js`, an `OffscreenCanvas` in the worker, called synchronously).
  - `Compression`, `simd`, `SwiftUI`, `UniformTypeIdentifiers`, `CoreVideo`, `Vision`: the small parts used. Subject selection (Vision) isn't available on the web.
  - zlib and SQLite are the real C libraries.
- **Files.** Pixelmator Pro documents are SQLite databases, which SQLite opens by path, so the WASI host (`engine/wasi.js`) keeps a small file system in memory. Package folders (`.easel`, `.pxd`) are zipped by the page on the way in.
